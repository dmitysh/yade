# executor-sessions Specification

## Purpose

Повседневное общение с установленными Claude Code и Codex внутри рабочих пространств с независимой историей, явным управлением выполнением и разрешениями.

## Requirements

### Requirement: Сессия выбранного исполнителя

Приложение ДОЛЖНО (SHALL) позволять создать в пространстве несколько отдельных сессий Claude Code и Codex. У каждой сессии должны быть собственная история, исполнитель и состояние выполнения, независимые от открытой вкладки.

#### Scenario: Два исполнителя в пространстве
- **WHEN** пользователь создаёт сессию Claude Code и сессию Codex в одном пространстве
- **THEN** доступны два независимых разговора с явно указанными исполнителями

#### Scenario: Закрытие представления
- **WHEN** пользователь закрывает вкладку выполняющегося разговора
- **THEN** разговор и его история не удаляются, выполнение не прерывается из-за закрытия представления

### Requirement: Параллельные сессии с общими файлами

Приложение ДОЛЖНО (SHALL) разрешать одновременную работу сессий в одном пространстве, отображать их активность и общность файлов. Автоматическое согласование правок разных исполнителей не предоставляется.

#### Scenario: Одновременная работа
- **WHEN** Claude Code и Codex выполняют задачи в одном пространстве
- **THEN** обе сессии видны как активные и работают с одной рабочей копией
- **AND** пользователь видит, что пространство используется несколькими сессиями

#### Scenario: Независимые изменения
- **WHEN** сессии запущены в разных Git worktree
- **THEN** каждая работает с файлами своего пространства
- **AND** приложение не объединяет результаты автоматически

### Requirement: Поток разговора и фактическое состояние

Приложение ДОЛЖНО (SHALL) отправлять сообщения выбранному исполнителю и отображать поток ответа, действия и состояния выполнения, ожидания ввода, завершения, ошибки и прерывания. Ошибка подключения или процесса не должна представляться успешным завершением.

#### Scenario: Поступление ответа
- **WHEN** исполнитель передаёт части ответа и действия
- **THEN** они появляются в соответствующем разговоре до завершения всего ответа

#### Scenario: Ошибка во время выполнения
- **WHEN** процесс исполнителя аварийно завершается либо соединение теряется
- **THEN** сессия показывает ошибку или прерывание с доступной причиной
- **AND** полученные сообщения остаются в истории

### Requirement: Адресация запросов разрешений

Приложение ДОЛЖНО (SHALL) показывать запросы разрешений и пользовательского ввода и передавать решение только создавшему запрос исполнителю, сессии и запуску. Устаревший запрос не должен разрешать действие нового запуска.

#### Scenario: Разрешения в двух сессиях
- **WHEN** две сессии одновременно ожидают разрешения
- **THEN** решение в одной сессии передаётся только её запросу
- **AND** вторая сессия остаётся в ожидании

#### Scenario: Устаревший запрос
- **WHEN** запуск завершился до ответа пользователя на его запрос
- **THEN** ответ не применяется к другому или новому запуску
- **AND** интерфейс сообщает, что запрос больше не актуален

#### Scenario: Отказ пользователя
- **WHEN** пользователь отклоняет запрос инструмента
- **THEN** исполнитель получает отказ и продолжает либо завершает работу согласно собственному поведению

### Requirement: Управляемая остановка

Приложение ДОЛЖНО (SHALL) позволять прервать выполнение выбранной сессии предусмотренным исполнителем способом и отображать подтверждённое состояние. Отправка запроса остановки сама по себе не считается завершением процесса.

#### Scenario: Остановка одной сессии
- **WHEN** пользователь останавливает одну из двух выполняющихся сессий
- **THEN** запрос направляется выбранному запуску
- **AND** другая сессия продолжает работу

#### Scenario: Остановка ещё не завершена
- **WHEN** запрос остановки отправлен, но исполнитель ещё работает
- **THEN** показано ожидание остановки, а сессия не объявлена завершённой

### Requirement: Явное продолжение штатной сессии

Приложение ДОЛЖНО (SHALL) продолжать сохранённый разговор по явному действию пользователя с использованием штатной сессии исполнителя. Отображаемая история не должна подменять его внутреннее состояние или автоматически повторять команды.

#### Scenario: Продолжение после перезапуска
- **WHEN** пользователь выбирает продолжение сохранённой сессии, а её данные исполнителя и пространство доступны
- **THEN** продолжается исходный разговор выбранного исполнителя

#### Scenario: Штатная сессия недоступна
- **WHEN** данные продолжения удалены либо выбранный исполнитель не может их открыть
- **THEN** показана причина
- **AND** новый разговор не выдаётся за успешно восстановленный

#### Scenario: Пространство отсутствует
- **WHEN** история сохранена после удаления пространства
- **THEN** историю можно читать, а выполнение в отсутствующем расположении не запускается

### Requirement: Привычные команды и вложения

Встроенное общение ДОЛЖНО (SHALL) предоставлять привычные поддерживаемые выбранным исполнителем команды и передачу файлов и изображений без отдельного обязательного этапа подготовки вложений. Совместимость должна быть проверена отдельно для обоих исполнителей; обязательные возможности не сокращаются молча.

#### Scenario: Обычная команда исполнителя
- **WHEN** пользователь вводит привычную команду, доступную выбранному исполнителю
- **THEN** она обрабатывается в соответствующей сессии с сохранением её назначения

#### Scenario: Файл или изображение
- **WHEN** пользователь передаёт поддерживаемое выбранным исполнителем вложение в сообщении
- **THEN** вложение доходит до выбранной сессии и используется согласно возможностям исполнителя

#### Scenario: Несовместимый способ передачи
- **WHEN** выбранное подключение не может передать запрошенную поддерживаемую возможность
- **THEN** пользователь видит причину, а операция не изображается успешной
- **AND** возможность не считается реализованной при приёмке
